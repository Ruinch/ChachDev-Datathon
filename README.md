Локальная проверка кассовых процедур по видео

Проект для кейса ForteBank на Datathon 26. Цель — принять запись `.mov`, найти визуально подтверждаемые эпизоды, показать таймкод и 1–3 настоящих кадра из исходного видео и связать наблюдение с проверенным нормативным пунктом РК. Вывод служит подсказкой проверяющему человеку.

## Экспериментальная ML-ветка

Добавлен локальный анализатор Qwen3.5/llama.cpp, совместимый с изолированным обработчиком сервиса, и импорт разметки с приоритетом заметок человека над гипотезами ИИ. Получены реальные результаты через API с исходными JPEG. Приёмка качества ещё не пройдена: сохраняются ошибки классов, ролей и таймкодов. На восьми отложенных файлах модель дала четыре ложные тревоги; оба поставляемых каталога остаются отключёнными. Исследовательские прогоны доступны отдельно и не активируют API. Порядок воспроизведения: [передача участнику 1](docs/ml-handoff.md), [фактические замеры и ограничения](docs/ml-measurements.md).

## Состояние проекта

Реализована **сервисная часть системы видеоконтроля**: рабочий кабинет с журналом проверок, загрузкой записи, просмотром результатов и каталогом процедур; защищённый API, постоянное хранение задач, проверка видео и контроль времени обработки. Экспериментальный ML подключается отдельной фабрикой. API проверяет готовность до принятия задачи: без анализатора, медиоинструментов и включённых проверенных правил загрузка для анализа недоступна. Работоспособность подключения не означает достаточное качество для жюри.

В интерфейсе доступны просмотр исходного видео, переход к таймкоду события, увеличение доказательного кадра, экспорт JSON и печать отчёта со всеми событиями и охватом проверки. Печать открывает стандартное окно браузера; отдельного серверного PDF-генератора нет. Если браузер блокирует скачивание JSON, ответ можно скопировать; при недоступном буфере обмена появляется текст для ручного копирования. Ссылку вида `/?job=UUID` можно открыть повторно: интерфейс восстановит задачу после ввода ключа. Состояние анализатора и лимиты читаются с сервера через `/api/v1/system`.

## Работа с сервисом

1. В разделе **«Подключение»** введите общий ключ доступа. Он используется во всех разделах в памяти текущей страницы: не записывается в `localStorage`/`sessionStorage`, URL или экспорт. После обновления страницы ключ нужно ввести заново.
2. **«Журнал проверок»** показывает сохранённые задачи, общую сводку, поиск по имени файла и фильтры статуса/вердикта. Страницы журнала загружаются с сервера; открытие строки получает полный результат отдельно. Сводка относится ко всем задачам, независимо от текущего фильтра.
3. В **«Новой проверке»** выберите MOV, просмотрите запись и запустите анализ. После принятия задачи сервис автоматически обрабатывает видео и показывает результат; ручного запуска кода для каждой записи не требуется. До подключения ML запуск недоступен с явной причиной.
4. В **результате проверки** откройте событие, перейдите к его времени в защищённом исходном видео, рассмотрите кадры и источник правила. Можно скопировать JSON, получить ссылку на задачу или открыть печать отчёта. Завершённые проверки сохраняются на сервере и доступны из журнала после повторного подключения.
5. **«Процедуры»** показывает правовую справку и отдельный каталог анализа. В справке — шесть сценариев, правильный порядок действий, возможные отклонения, необходимый контекст, исключения, официальные источники и редакции. Каталог показывает фактическое состояние распознавания и причину отключения кандидатов; чтение справки не включает их в анализ. Источники и порядок применения подробно описаны в [правовых основаниях](docs/legal-basis.md).

Изученное ТЗ требует результат за 5 минут, полностью локальную обработку без облачных AI-сервисов, несколько нарушений в одном видео и JSON со статусами `processing`, `done`, `failed`. Кадры в ответе API должны быть JPEG в base64. Анализ звука и идентификация лиц запрещены. Архив датасета и его видео не следует добавлять в репозиторий или публиковать.

Локальный архив организаторов содержит 42 MOV и таблицу с 42 строками: 22 помечены как нарушение, 20 — как отсутствие нарушения. Первоначальная разметка положительной записи задаёт отдельную временную точку без интервала; теперь импортируются также ручные заметки пользователя и неподтверждённые интервалы ИИ с приоритетом человеческих наблюдений; длительность записей меньше трёх минут. Дубликаты и спорную разметку нужно согласовать локально до оценки. Идентификаторы записей, их индивидуальные временные отметки и содержимое разметки остаются только в закрытых локальных материалах. Кадры не просматривались через облачный AI.

## Быстрый локальный запуск

Автоматический запуск рассчитан на **Windows / Python 3.12–3.13**. Для создания новой `.venv` нужен Python Launcher с Python 3.13 (`py -3.13`); существующая ML-среда Python 3.12 сохраняется. В PowerShell из корня проекта:

```powershell
.\scripts\setup.ps1
.\scripts\start.ps1
```

`setup.ps1` создаёт отсутствующую `.venv`, устанавливает закреплённые зависимости сервиса и создаёт отсутствующий `.env` со случайным ключом. Ключ в терминал не выводится; откройте локальный `.env` и используйте `APP_API_KEY` для подключения. Существующая конфигурация сохраняется без изменений, а неподходящая `.venv` не пересоздаётся автоматически. Скрипт не устанавливает модели, CUDA или веса.

Для обработки нужны локальные **FFmpeg и FFprobe**. Скрипты автоматически находят `.local_tools/ffmpeg/bin/ffmpeg.exe` и `ffprobe.exe`, затем используют стандартные команды из `PATH`; свои пути задаются в `APP_FFMPEG_BIN` и `APP_FFPROBE_BIN`. Бинарные файлы нужно подготовить отдельно. Для проверки уже установленной среды без скачивания пакетов выполните `.\scripts\setup.ps1 -SkipInstall`.

Откройте [локальный интерфейс](http://127.0.0.1:8000/) и введите ключ. Чтобы посмотреть интерфейс до установки медиоинструментов, используйте `-AllowMissingMediaTools` для setup и start; анализ при этом останется недоступен. Обычный start проверяет среду и не устанавливает пакеты. Node.js нужен только для тестов интерфейса, а не для работы сервиса. При ограничении запуска PowerShell-скриптов можно выполнить `powershell -ExecutionPolicy Bypass -File .\scripts\start.ps1` для одного процесса.

`constraints.txt` закрепляет окружение сервиса и тестов, включая зависимости проверки изображений. Пакеты ML, CUDA и веса в него не входят: их подбирает человек 2. После установки пакетов модели повторите тесты сервиса. Для другой версии Python/ОС сначала подтвердите совместимость зависимостей отдельно.

Данные задач сохраняются в `.local_data/` и игнорируются Git. `.env` также исключён из Git. Значения, уже заданные в окружении процесса, имеют приоритет над `.env`; подстановка команд и переменных внутри `.env` не выполняется. Скрипты можно вызывать из другого каталога: пути данных, правил и инструментов всегда разрешаются от корня проекта. Для отдельной конфигурации передайте `-EnvPath C:\private\service.env` в setup, start и check. До подключения модели загрузка для анализа возвращает HTTP 503 с причиной неготовности. Формат адаптера описан в [инструкции для ML](docs/ml-integration.md).

Проверки окружения и тесты (для `-RunTests` нужен Node.js 22+):

```powershell
.\scripts\check.ps1 -AllowMissingMediaTools -RunTests
# После подключения модели, правил и запуска сервера:
.\scripts\check.ps1 -BaseUrl http://127.0.0.1:8000 -RequireAnalyzer
```

`-RunTests` последовательно проверяет Python/API, поведение модулей интерфейса и Windows-скрипты без сетевой установки. Тесты запускателей используют временные конфигурации и сохраняют проектный `.env`.

Все настройки и порядок публичного запуска: [развёртывание](docs/deployment.md). Границы модулей и эксплуатационные ограничения: [архитектура сервиса](docs/service-architecture.md). Что проверить перед сдачей: [приёмка](docs/acceptance.md).

Интеграционные проверки `tests/test_pipeline_integration.py` генерируют синтетический `.mov`, используют настоящие FFmpeg/FFprobe и проверяют путь до JPEG/API. Они не измеряют качество модели. Без медиоинструментов эти проверки пропускаются; отдельный запуск с заданными путями описан в [инструкции развёртывания](docs/deployment.md#проверка-на-локальной-машине).

## Контракт API

Все пути `/api/v1/` защищены заголовком `X-API-Key`. Используется один общий ключ: он даёт доступ ко всем задачам сервиса, отдельных аккаунтов и разграничения задач по пользователям нет.

Интерактивная документация доступна по адресу [локальная документация API](http://127.0.0.1:8000/docs). Swagger использует локальные ресурсы и открывается без обращения к внешнему CDN; для выполнения API-запросов укажите общий ключ через `Authorize`.

| Метод и путь | Назначение |
| --- | --- |
| `GET /api/v1/system` | Готовность анализатора, медиоинструментов и правил, лимиты, занятость сервера. |
| `GET /api/v1/jobs` | Журнал без кадров и описаний событий, фильтры и общая статистика. |
| `GET /api/v1/rules` | Каталог процедур, включая отключённых кандидатов, состояние проверки и нормативные источники. |
| `GET /api/v1/legal-guide` | Правовая справка с официальными источниками, редакциями, правильным порядком действий, исключениями и достаточностью доказательств; не активирует ML-правила. |
| `POST /api/v1/analyze` | Multipart поле `file` с настоящим `.mov`. При принятии — HTTP 202 и `{"job_id":"...","status":"processing"}`. |
| `GET /api/v1/jobs/{job_id}` | Статус и результат; дополнительные метаданные задачи находятся в `metadata`. |
| `GET /api/v1/jobs/{job_id}/video` | Исходное видео для проверки таймкодов, включая запросы диапазонов байтов. |

Параметры `GET /api/v1/jobs`: `q` — регистронезависимый поиск буквальной подстроки в имени файла (до 255 символов); `status=all|processing|done|failed`; `verdict=all|violation|no_violation`; `limit` — размер страницы от 1 до 100, по умолчанию 20; `offset` — смещение от 0. Ответ содержит `items`, число совпадений `total`, `limit`, `offset` и общую `summary` со счётчиками `total`, `processing`, `done`, `failed`, `violation`, `no_violation`. Результаты идут от новых к старым. Элементы журнала содержат метаданные, число событий и охват проверки; полные события и JPEG запрашиваются по `GET /api/v1/jobs/{job_id}`.

`GET /api/v1/rules` возвращает `items`, `enabled_count` и `total`. Для каждой процедуры доступны `enabled`, `verification` (`candidate` или `verified`), `verified_on`, нормативная ссылка, наблюдаемые признаки, необходимый контекст, ограничения и примечание проверки. Статус кандидата не означает, что процедура распознаётся. При недоступном или ошибочном каталоге сервер возвращает HTTP 503.

Пример структуры успешного ответа после подключения анализатора и проверенного правила; значения иллюстративные, JPEG сокращён:

```json
{
  "job_id": "3f2a9c1e-0e97-4a27-bfe2-53f61248b324",
  "status": "done",
  "verdict": "violation",
  "analysis_scope": {
    "full_video_checked": true,
    "checked_rule_ids": ["CHECKED_RULE_1"],
    "enabled_rule_ids": ["CHECKED_RULE_1"],
    "limitations": []
  },
  "violations": [
    {
      "type": "Наблюдаемый тип события",
      "timecode_sec": 44.2,
      "description": "Что видно в записи и почему это требует проверки",
      "evidence_frames": [
        { "timestamp_sec": 44.2, "image_base64": "/9j/4AAQ..." }
      ],
      "rule": {
        "title": "Правила ведения кассовых операций",
        "clause": "пункт 20",
        "source_url": "https://old.adilet.zan.kz/rus/docs/V1900019680"
      }
    }
  ]
}
```

`rule` — дополнительное поле для нормативной ссылки, требуемой пользовательским сценарием. Поле `analysis_scope` всегда описывает охват успешной проверки: проверенные/включённые правила, ограничения и полноту просмотра. Подтверждённые события можно вернуть с `verdict=violation` при частичной проверке, явно указав `full_video_checked=false` и ограничения. При `no_violation` массив `violations` пуст и требуется полная проверка записи по всем включённым правилам без нерешённых ограничений. Это вывод только по поддерживаемым процедурам.

Техническая ошибка принятой задачи возвращается со статусом `failed` и полем `error`, без фиктивного вердикта. Сервер извлекает кадры из исходного файла по вычисленным таймкодам и подставляет нормативную ссылку из каталога; модель возвращает идентификатор правила.

Отказ до принятия задачи не создаёт `job_id`: HTTP 401 — неверный ключ, 503 — система не готова, 429 — обработчик занят, 408 — истекло время загрузки, 413 — превышен лимит размера или длительности, 422 — файл не является пригодным видео. У таких ответов поле `detail` содержит причину. Клиенту следует показывать её и предлагать повторить действие после устранения причины.

## Устройство

```text
frontend/       рабочий кабинет, журнал, процедуры и результаты
  session.js    единое состояние подключения, файла, задачи, маршрута и опроса
  app.js        отображение загрузки, обработки и результата
  service.js    отображение навигации, подключения, журнала и процедур
  api.js        защищённые запросы, готовность и ошибки API
  media.js      исходный видеоплеер, таймкоды, увеличение кадров и экспорт JSON
app/main.py     сборка приложения, жизненный цикл, сайт и локальная API-документация
app/job_service.py приём и сохранение видео, готовность и жизненный цикл задач
app/http_api.py HTTP-маршруты и представление ответов
app/http_guard.py авторизация и ограничения потока загрузки
app/storage.py  SQLite и локальные файлы задач
app/analyzer.py контракт локального анализатора и загрузка фабрики
app/evidence.py извлечение JPEG из исходного видео через FFmpeg
app/schemas.py  схема ответа жюри и нормативные ссылки
scripts/        локальный запуск и проверка окружения
docs/           интеграция ML, развёртывание, приёмка, правила и оценка
tests/          проверки сервиса, API-контракта и отказов
  frontend/     проверки состояния сессии и поведения HTTP-клиента
```

`JobService` координирует приём файла, проверку видео и передачу задачи существующему обработчику; HTTP-маршруты не управляют файлами или SQLite. Журнал и получение оригинала читают только нужные метаданные, не загружая JPEG результата. Граница локального ML остаётся в `app/analyzer.py` и существующих схемах.

`WorkspaceSession` владеет ключом, выбранным файлом, задачей и маршрутом страницы. Представления подписываются на его состояние. Запросы относятся к конкретному подключению: ответ старого запроса не может вернуть прежний ключ или подменить новую задачу. Опрос активной задачи продолжается при просмотре журнала; повторное нажатие не создаёт вторую загрузку.

Сервер запускается в **одном процессе Uvicorn**; блокировка каталога данных отвергает второй экземпляр сервера. Один отдельный процесс выполняет принятую задачу; параллельная загрузка для анализа получает HTTP 429. Очереди нет, чтобы ожидание не скрывало превышение пяти минут. Таймаут задачи включает инициализацию адаптера, анализ и извлечение кадров; отдельные таймауты ограничивают приём файла и проверку контейнера. Их сумма не превышает 295 секунд (по умолчанию 285). Прерванные при рестарте задачи помечаются `failed`. Адаптер Qwen использует отдельный заранее загруженный llama.cpp на loopback, поэтому запуск весов измеряется дополнительно к времени API. Фактические замеры и границы проверки приведены в [ML-отчёте](docs/ml-measurements.md).

## Следующие этапы

По ТЗ готовый сервис означает автоматический полный путь от новой записи до результата. Для сдачи должны быть выполнены пять условий:

1. Новый MOV проходит `processing → done` через интерфейс и API без ручного запуска обработки; несколько событий возвращаются в одном результате.
2. Вердикт подтверждается наблюдаемыми действиями: для каждого события доступны тип, точный таймкод, 1–3 исходных JPEG и обоснованная нормативная ссылка. Неполный анализ не выдаётся за отсутствие нарушений.
3. Загрузка и ошибки обработаны, результаты переживают обновление страницы и перезапуск сервера, зависшая задача не блокирует дальнейшую работу.
4. Полный цикл с холодного запуска модели занимает не более 300 секунд на машине сдачи; после подготовки весов анализ работает без исходящего интернета.
5. Интерфейс и API доступны жюри из другой сети по публичному HTTPS-адресу с ключом; переданы инструкции, версии моделей, поддерживаемые процедуры и измеренные ограничения.

Журнал, каталог и печать упрощают работу проверяющего. Реальная модель интегрирована экспериментально. Для подтверждения готовности всего решения остаются приёмка качества и применимости правил, проверка полного времени на машине сдачи и публичный запуск.

| Этап | Работа | Условие перехода |
| --- | --- | --- |
| 1. Локальный просмотр данных | Состав, метки и длительности проверены; импортированы ручные заметки и вторичные гипотезы ИИ. Нужно подтвердить интервалы, роли и спорную разметку. | Есть 2–3 доказуемых кандидата, согласованные метки и независимая проверочная часть. |
| 2. Декодер и замер модели | Локальная среда подготовлена, сравнения Qwen3-VL/Qwen3.5 и реальные API-прогоны выполнены. Итоги и ограничения записаны в ML-отчёте. | Известны время полного прохода, память и ошибки качества. |
| 3. Анализатор событий | Реализованы окна, исходные таймкоды, повторная проверка, объединение событий и подключение к каталогу. Распознавание требует исправления. | Автоматический JSON содержит несколько корректных событий и только исходные кадры. |
| 4. Независимая проверка | Проверка восьми файлов одной камеры дала 50% совпадений и четыре ложные тревоги. Нужны исправление модели и новый набор проверки; текущая модель приёмку не прошла. | Качество принято, полный цикл занимает меньше 5 минут с запасом. |
| 5. Публичный запуск | Проверить ключ, URL жюри, параллельные загрузки, перезапуск и работу без исходящего интернета. | Есть работающий публичный интерфейс/API и инструкция для сдачи. |

В команде **два человека**. Человек 1 ведёт интерфейс, API, хранение, извлечение кадров, защиту и развёртывание. Человек 2 ведёт локальный просмотр датасета, выбор/настройку модели, адаптер анализатора и оценку качества. Вместе подтверждают применимость правил и проверяют полный путь на отложенных видео. Совместная контрольная точка — первый реальный результат на длинном ролике и согласование типов событий до настройки порогов.

Подробности: [кандидатные правила](docs/rules.md) и [протокол выбора модели](docs/model-evaluation.md). Исходное ТЗ — `Кейс_ForteBank.docx` из папки организаторов; оно не включено в репозиторий.
