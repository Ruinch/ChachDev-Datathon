# Правовые основания и пределы видеопроверки

Проверено 18 октября 2026 года. Публичная справка сервиса находится в `app/data/legal-guide.json`, доступна в разделе «Процедуры» и через защищённый `GET /api/v1/legal-guide`. Она объясняет требования и исключения. Исполняемые правила анализа по-прежнему задаются отдельным `app/data/rules.json`.

## Какие материалы проверены

Основной источник — [постановление Правления НБРК от 29.11.2019 № 231](https://old.adilet.zan.kz/rus/docs/V1900019680), зарегистрированное 03.12.2019 под № 19680. Оно утверждает Правила осуществления кассовых операций и операций по инкассации банкнот, монет и ценностей в банках второго уровня, филиалах банков-нерезидентов Республики Казахстан, Национальном операторе почты и указанных инкассаторских организациях. Область действия установлена [пунктом 1](https://old.adilet.zan.kz/rus/docs/V1900019680#z42). Бытовую кассу магазина нельзя автоматически оценивать по этим банковским правилам.

Прочитаны полный официальный консолидированный HTML, [история редакций](https://old.adilet.zan.kz/rus/docs/V1900019680/history) и [официальный архив на 01.01.2020](https://old.adilet.zan.kz/rus/archive/docs/V1900019680/01.01.2020). Последняя дата редакции в прочитанной истории — **12.07.2026**, статус документа — «Обновленный». Источник указывает обновление базы 16.10.2026 и включение документов по 14.10.2026. Это граница проверенного источника, а не гарантия отсутствия последующих изменений.

Из предоставленного файла «Сводный_разбор_42_видео.xlsx» локально извлечены структура, агрегаты реестра и официальная ссылка: 42 записи, 40 уникальных видеорядов по признаку в колонке K. Источник в ячейке `Исходные метки!B72` ведёт на [PDF редакции 01.01.2020](https://zan.gov.kz/api/documents/136659/rus/01.01.2020/download/pdf). Этот PDF не читался; исторический текст сверен через официальный HTML-архив. Описания отдельных роликов, кадры и исходные видео во внешние AI-сервисы не передавались. Метки таблицы не принимаются за правовую квалификацию.

Публичные снимки источников, URL и SHA256 сохранены локально в игнорируемой папке `.local_data/legal-research/`. Саму таблицу, её подробные выводы и видео в публичную справку переносить нельзя.

При локальном согласовании с человеком 2 поля таблицы используются так:

| Поле таблицы | Роль в проверке |
| --- | --- |
| «Метка Excel» | Исходная разметка для сопоставления. Не заменяет доказательство и пункт нормы. |
| «Рабочий класс», «Категория», «Тема» | Гипотеза для выбора процедуры. Не добавляет новый юридический запрет. |
| «Видимый факт» | Наблюдение для ручной сверки с непрерывным исходным фрагментом. |
| «Что не установлено / предел вывода» | Недостающие обязательные факты; их нельзя заполнять предположением модели. |
| Границы контекста и активного эпизода | Указатель для просмотра и локализации. Время проверяется по исходному видео. |
| «Канонический файл», «Уникальный видеоряд» | Контроль дубликатов при делении и оценке; копии одного видеоряда не дают независимых примеров. |

Чтобы связать конкретную строку с нормой, локально подтверждают тип операции, роль участников, дату записи, все обязательные факты и исключения. Публичная справка не объявляет какие-либо строки этой таблицы доказанными нарушениями.

## Как объяснять процедуру

Последовательность проверки: наблюдаемое действие → вид операции → все условия применимой нормы → исключения → достаточность доказательств → объяснение со ссылкой. Условия видимости ниже являются инженерной методикой проекта. Они не цитируются как дополнительные требования закона.

Автоматические устройства из [пункта 6](https://old.adilet.zan.kz/rus/docs/V1900019680#z72) требуют отдельного определения сценария.

Для монет пункт 32 предусматривает выдачу по надписям на установленной упаковке и пересчёт по кружкам из неполных мешков. Класс для банкнот нельзя переносить на монеты без учёта этих правил.

## Почему важна дата записи

По рассматриваемому смыслу пункты 20, 22, 31(4), 32 и 42 совпадают в прочитанных архиве 01.01.2020 и текущем тексте. Это не подтверждает одинаковость всех промежуточных редакций и всего акта. В редакции 01.01.2020 пункт 12 ещё не содержал нынешнего абзаца об исключениях для лекарств и средств связи; в текущем тексте он относится к изменению от 10.11.2025 № 71. Дата введения изменения определяется по акту и официальному опубликованию, а не только по дате подписания.

Дату операции нужно получить из надёжного источника: материалов организатора или подтверждённых данных записи. Время изменения файла и порядковый номер видео сами по себе не доказывают её. Если дата неизвестна, применимая редакция остаётся неустановленной. Текущую справку нельзя автоматически выдавать за норму, действовавшую в день съёмки.

## Что в проекте уже защищает обоснование

- Анализатор возвращает наблюдение и `rule_id`. Сервер подставляет нормативный источник из каталога; модель не выбирает произвольную ссылку.
- Кадры извлекаются из исходника FFmpeg, время проверяется относительно длительности видео.
- `no_violation` допустим только для полного охвата активных процедур. Нехватка доказательств без подтверждённых событий не превращается в отрицательный вердикт.
- При подтверждённых событиях и неполном анализе сохраняются `full_video_checked=false` и ограничения.
- Карточка, JSON и печатное содержимое сохраняют нормативную ссылку результата. Справка текущей редакции показана отдельно.

У сохранённого события сейчас нет `rule_id`, версии каталога, даты операции и даты юридически применённой редакции. Поэтому нельзя автоматически связать старое событие с новой карточкой справки или написать, что справка определённой версии применялась при анализе. Новое поле API `result_binding="reference_only"` прямо сохраняет этот предел. Изменять ML-контракт ради этой справки не потребовалось.

Для будущей совместной доработки с человеком 2 полезно согласовать сохранение версии каталога, идентификатора правила, даты операции/статуса её подтверждения и версии применённой нормы. Это отдельная интеграционная задача; текущая справка такие сведения не придумывает.

## Правовая часть эксплуатации сервиса

Правила поведения кассира и основания обработки банковских видео — разные вопросы. Локальный инференс и API-ключ не подтверждают выполнение всех требований к данным.

По полному официальному тексту [Закона РК от 21.05.2013 № 94-V «О персональных данных и их защите»](https://old.adilet.zan.kz/rus/docs/Z1300000094), полученному 18.10.2026:

- **Статья 7:** установить законное основание сбора/обработки. Общее правило согласия имеет предусмотренные законом исключения; цель должна быть заранее определённой, объём — необходимым.
- **Статьи 11 и 14:** обеспечивать конфиденциальность ограниченных данных и использовать их для ранее заявленных целей. Разрешение организатора на учебный датасет нельзя автоматически считать разрешением на публикацию видео.
- **Статья 12:** хранение базы/цифрового объекта на территории РК; срок определяется достижением целей, если законодательство не предусматривает иное. Размещение сервера и резервных копий нужно подтвердить, а не выводить из слова «локальный».
- **Статья 16:** отдельно оценить трансграничную передачу. Условия задания о запрете облачных AI выполняются независимо от того, допускает ли конкретную передачу иной правовой режим.
- **Статья 19-1:** автоматизированная обработка, изменяющая права или законные интересы, имеет отдельные ограничения и обязанности. Не подключать отчёт к автоматическому взысканию с работника или иному правовому решению без отдельной проверки основания и процедуры.
- **Статья 22:** нужны меры защиты и предотвращения несанкционированного доступа. Один общий ключ проекта открывает все задания; разграничения по пользователям, аудита доступа и автоматического срока удаления сейчас нет.

Операционные сведения о клиентах могут относиться к банковской тайне: [статья 69 Закона РК от 16.01.2026 № 258-VIII «О банках и банковской деятельности»](https://old.adilet.zan.kz/rus/docs/Z2600000258). Для старых операций проверяются действовавший закон и переходные положения. Не каждый пиксель видео автоматически является банковской тайной, но отображение операции и данных клиента требует оценки содержания и правомерного доступа.

Перед работой с реальными банковскими записями владельцу сервиса нужно определить получателей доступа, основание обработки, размещение, срок хранения и порядок удаления/резервирования. Это фактические незакрытые вопросы эксплуатации, а не выполненные возможности приложения. Для публичной демонстрации до их решения подходят синтетические материалы.

## Активация и обновление

Правовой источник сверен, но `R20-A` и `R20-B` остаются отключёнными кандидатами. Их ID, условия наблюдаемости и ML-интерфейс сохранены. Исправлены только точные абзацы и запись о состоянии проверки источника. Остальные четыре процедуры — справочный материал без новых исполняемых классов.

После согласования даты редакции нужны локальные примеры, подтверждение видимости всех условий и измеренная проверка анализатора. Только затем меняются `verification`, `verified_on` и `enabled` в исполняемом каталоге. После изменения `rules.json` сервер перезапускается: API читает каталог при старте, обработчик — перед задачей. Изменять его во время обработки как способ обновления нельзя.

Для каждого обновления справки меняются версия и дата сверки; проверяются официальный текст, история, исключения и ссылки. Успешная проверка структуры JSON подтверждает формат и связи, но не истинность юридической интерпретации.
