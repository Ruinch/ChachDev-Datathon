# Замеры локального анализатора

## Обновление 18 октября 2026

Локальный Qwen3.5-4B Q4_K_M подключён к актуальному API через `app.local_analyzer:build_analyzer`. Реальный MOV проходит отдельный процесс обработки, а сервер извлекает настоящие JPEG. Это рабочий экспериментальный конвейер, **не принятый по качеству детектор**. Основной и исследовательский каталоги в репозитории отключены по результатам оценки. Положительная проверка формата и исходных JPEG не равна приёмке распознавания.

Человеческие заметки прочитаны как основной источник. Вторичный разбор ИИ и его интервалы сохранены отдельно как неподтверждённые предложения. Ни то, ни другое не используется для подстановки предсказаний. Подтверждённой ручной интервальной разметки для оценки типов и границ пока нет. Все описания были изучены при разработке; результаты на том же наборе не являются слепой внешней проверкой.

Среда замеров человека 2: Windows, Python 3.12, RTX 4050 Laptop 6 ГБ, Ryzen 5 7535HS, 16 ГБ ОЗУ. Runtime llama.cpp b11669 / CUDA 12.4; контекст 16384, один слот выполнения, flash attention, 256–768 visual tokens/image. Декодирование 2 FPS, окна 24 с с шагом 18 с, 12 кадров на окно, до 16 при повторной проверке, длинная сторона до 848 px. Бюджет анализатора — 210 с. Веса и SHA-256 закреплены в `model35-lock.json` и `model35-9b-lock.json`. Текущая машина человека 1 с GTX 1650 Ti 4 ГБ и Python 3.13.15 отличается; приведённые времена и память для неё не измерены.

| 4B, первая версия условий R20-C | 4 / 1 / 1 / 0 / 0 | 5/6 | 20,743 / 89,593 | 1 из 4 положительных предсказаний |
| 4B, уточнённые роли и более узкие условия R20-C | 3 / 1 / 1 / 1 / 0 | 4/6 | 28,587 / 160,688 | 1 из 3 положительных предсказаний |
| 9B Q4_K_M, те же условия, 24 слоя на GPU | 0 / 0 / 1 / 3 / 2 | 1/6 | 69,531 / 210,078 | Нет положительных предсказаний |
| 4B, повтор после уточнения о разных ракурсах (v3) | 3 / 1 / 1 / 1 / 0 | 4/6 | 18,266 / 66,469 | 2 из 3 положительных предсказаний |

Один ложный положительный результат был на самом длинном отрицательном видео. Есть путаница ролей, банкнот и документов, типов и времени события. Первая версия имеет более высокий двоичный показатель, но это не подтверждает правильность её событий; она не выбрана по одному этому числу. Значения выше — диагностический подбор настроек, не итоговая оценка.

9B с частичным переносом на CPU не выбран: два длинных прохода исчерпали бюджет; peak VRAM 5874 MiB. Дополнительно проверен 4B с `--reasoning on --reasoning-budget 512` на трёх коротких dev-видео: 0 TP, 1 TN, 2 FN, 0 отказов, максимум 19,578 с. Этот режим также не выбран. Для дальнейшей проверки зафиксирован 4B с уточнёнными условиями, `--reasoning off`, всеми слоями на GPU. Его недостаточное качество прямо отражено выше.

Исходная двоичная метка охватывает больше процедур, чем четыре экспериментальных класса. Поэтому таблица показывает только совпадение с исходной задачей. Она не измеряет качество каждого класса. Расстояние до одной исходной точки не проверяет лишние события, границы интервала, пригодность кадров и правовую квалификацию. GPU peak для двух прогонов 4B — около 4760 MiB общей занятой VRAM, опрос раз в 0,5 с.

После уточнения пользователя о разных ракурсах выполнен повтор v3 на той же диагностической шестёрке. Промпт требует определять роли в каждой последовательности по действиям, прослеживать роль уходящего человека до его ухода и не использовать постоянную сторону кадра. При неопределённой роли модель должна отмечать недостаток контекста, а не подтверждать событие. Это инструкция модели, а не доказанная гарантия правильного определения ролей. Двоичная точность не выросла: сохраняются FP и FN. Совпадений с исходной точкой стало два вместо одного; эталонного типа и интервала по-прежнему нет. Все шесть запросов завершились, peak VRAM 4438 MiB. Время относится к одному повтору анализатора с загруженными весами, не к холодному API и не к гарантированному ускорению. V3 оставлен исследовательским; каталоги не активированы. Восемь ранее отложенных файлов для этого изменения не использовались и повторно не оценивались.

### Проверка зафиксированных настроек на восьми отложенных файлах

После выбора 4B с уточнёнными условиями и выключенным мышлением выполнен проход `video-holdout`: 8/8 технически завершённых запросов, **4 TP, 4 FP, 0 TN, 0 FN**, совпадение с исходными метками **50%**. Модель выдала положительный вердикт на каждом файле. Precision = 0,5, recall = 1,0; высокий recall здесь не достоинство, поскольку пропущены все отрицательные случаи. Максимум 107,531 с, медиана 30,813 с, peak VRAM 4759 MiB. Три из четырёх положительных предсказаний находятся в пределах ±5 с от исходной точки; это не подтверждает их тип или нормативное основание.

Для этого прогона настройки были зафиксированы заранее. Группы точных дубликатов разделены; спорная положительная пара исключена. По уточнению пользователя 18.10.2026, записи имеют разные ракурсы и расположение кассиров. Предыдущее утверждение об одной камере было ошибочным и не основывалось на проверенной группировке. Принадлежность отдельных роликов к камерам и сессиям пока не размечена. Текстовые заметки изучены при разработке, поэтому это проверка на отложенных файлах, но не слепой внешний тест и не подтверждение переноса на новый ракурс. Численные результаты прогона сохранены без изменений.

**Решение:** модель непригодна для автоматической сдачи в текущем виде. Не активировать публичный API на основании этого результата. Оба репозиторных каталога оставлены кандидатными; локальные `evaluate`/`analyze` доступны для дальнейшего исследования. Следующее содержательное улучшение требует подтверждённых ролей и интервалов, положительных и похожих отрицательных примеров по конкретным поддерживаемым процедурам. Новый тест после исправления должен использовать отдельные данные; повтор этих восьми файлов считается диагностическим.

При объединении сервиса выявлена дополнительная граница применимости R22: пункт 22 относится к приёму наличных, а текущий критерий модели `service_started` описывает обслуживание шире. Уточнение каталога не меняет промпт и не подтверждает правильность существующих предсказаний. До активации человеку 2 нужно явно проверять приём наличных и повторить оценку с похожими отрицательными примерами других операций. Это незавершённая ML-задача; приведённые результаты измерений не пересчитывались.

### Проверка реального API

Первый полный локальный прогон Qwen3.5-4B: `processing → done / violation`, одно событие, три декодируемых JPEG, **34,969 с**. Измерение включает приём файла, проверку метаданных, новый процесс анализатора и извлечение кадров; llama.cpp к этому моменту уже загружен. Этот прогон подтверждает техническую интеграцию, а не правильность предсказанного события. Его приватные результаты и временный экспериментальный каталог сохранены отдельно от основной базы сервиса; активный каталог не публикуется. Повторить API-тест без принятого каталога нельзя: это намеренное ограничение готовности.

После слияния последнего исправления кадров из сервисной части самый длинный ролик (142,533 с) прошёл через API за **143,093 с**, вернул три события и восемь валидных JPEG. Правильность обнаружения этим техническим результатом не подтверждается. Отдельный короткий прогон прошёл за **18,953 с**, `done / no_violation`, без событий. Эти два результата проверяют фактический поток ответов, но не отменяют провал отложенной оценки.

После остановки предыдущего runtime выполнен ещё один полный прогон самого длинного видео с новым процессом Qwen3.5-4B: **149,760 с** от запуска модели до завершения локального API-теста. Из них готовность runtime — 7,577 с, путь API — 141,063 с; получены три события и восемь валидных JPEG. Процесс модели после теста остановлен. ОС не перезагружалась, файловый кеш мог сохраняться. Использовался локальный TestClient и отдельный реальный worker; публичный HTTPS и клиентская сеть в этот замер не входят. Системное блокирование исходящего интернета не проверялось; runtime запущен с `--offline`, запросы модели технически ограничены loopback. Один успешный замер времени не компенсирует ошибки распознавания и не является гарантией SLA на других файлах.

## Архив замеров 17 октября 2026

Модели запускаются на GPU и принимают реальные кадры через loopback, но приёмку качества не прошли. На исследованной dev-части нет успешно подтверждённых результатов. Быстрое завершение с `failed` не подтверждает пятиминутный SLA готового решения.

Машина: RTX 4050 Laptop, 6141 MiB VRAM, Ryzen 5 7535HS, 16 ГБ ОЗУ, Windows. Python 3.12, llama.cpp b11669 / CUDA 12.4. Веса и проекторы закреплены по ревизии и SHA-256 в `ml_tools/model*-lock.json`. Runtime запускался с `--offline`, одной GPU-очередью, context 8192 и flash attention. Время включает декодирование и обращения к модели, исключает загрузку весов, HTTP-загрузку видео и сборку итоговых кадров API.

Пик опрашивался раз в 0,5 с; возможны краткие незафиксированные выбросы. ОЗУ процесса и холодный старт не измерены отдельным воспроизводимым тестом.

Accuracy/precision/recall на завершённых запросах не определены. Доля правильных ответов среди всех запросов = 0. Это не утверждение, что видео не содержат нарушений.

8 holdout-файлов не анализировались моделью для настройки. 2 файла с противоречивыми точечными метками находятся в quarantine. Точная отрицательная пара дубликатов учитывалась как одно видео. Ручных классов/интервалов ещё нет, поэтому событийное качество и юридическая применимость к отдельным эпизодам не измерены.

## Что проверено отдельно

Модель правильно определила красный цвет искусственного одноцветного изображения. Это проверка передачи изображения, не распознавания банковских процедур. В тестах проверены декодирование искусственного `.mov`, получение настоящих JPEG через FFmpeg, временные границы, несколько событий, объединение повторов, запрет удалённых endpoint и редиректов, игнорирование proxy, отказ на повреждённых видео и невалидном JSON, разделение дубликатов и защита от утечки групп в holdout.

Проверка полного процесса с системно заблокированным исходящим интернетом ещё не выполнена. Зафиксированы локальные файлы весов, `--offline` у llama.cpp и техническое ограничение Python-клиента на loopback. Публичный URL, отказ HTTP 429 при конкурентном анализе и SLA относятся к интеграционной приёмке участника 1; очереди ожидания у сервиса нет.

## Следующее действие

В локальном инструменте `ml_tools/review.html` начать с 4 dev-роликов: короткого положительного, короткого отрицательного, более длинного положительного и самого длинного. Записать видимое действие, его интервал и применимый пункт; если три кандидата R20-A/R20-B/R22 не соответствуют данным, изменить каталог на основании наблюдений и проверенной нормы. Полную разметку всех записей сейчас делать не обязательно для первого выбора классов. Она нужна для окончательной проверки групп и оценки на holdout.

Не включать детектор для жюри до положительной приёмки. Не подставлять Excel-метки или известные таймкоды вместо вывода модели. Полные результаты, описания и исходные данные хранятся только в `.local_ml/`; в журнале приведены технические агрегаты.
