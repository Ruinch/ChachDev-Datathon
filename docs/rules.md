# Каталог визуальных процедур

Машиночитаемый каталог находится в `app/data/rules.json`. Сейчас он содержит два **отключённых кандидата**: `R20-A` и `R20-B`. Включённых нормативных правил нет, поэтому сервис не может выдавать успешное «нарушений нет» до проверки и активации каталога.

18.10.2026 получены полный [официальный текст постановления НБРК от 29.11.2019 № 231](https://old.adilet.zan.kz/rus/docs/V1900019680), [история](https://old.adilet.zan.kz/rus/docs/V1900019680/history) и [архив на 01.01.2020](https://old.adilet.zan.kz/rus/archive/docs/V1900019680/01.01.2020). В истории последняя дата редакции — 12.07.2026; база указывает документы по 14.10.2026. Ранее недоступный текст теперь сверен. Это подтверждение источника; наблюдаемость всех условий, дата применимой редакции и качество анализатора ещё не подтверждены, поэтому кандидаты остаются отключёнными.

Отдельная справка `app/data/legal-guide.json` объясняет шесть процедур, исключения и пределы вывода. Она доступна через `GET /api/v1/legal-guide` и в разделе «Процедуры», не активирует правила и не подменяет нормативную ссылку старого результата. Подробный разбор и источники: [правовые основания](legal-basis.md).

| ID | Кандидат и проверенный нормативный пункт | Необходимый видимый контекст | Когда нельзя делать вывод |
| --- | --- | --- | --- |
| `R20-A` | Приём или пересчёт внесённых денег без присутствия клиента; пункт 20, абзац первый. | Непрерывно видны передача клиентом наличных, их приём или пересчёт; полностью видна клиентская зона; установлено назначение операции. | Клиент вне кадра, зона видна частично, неизвестна принадлежность денег или это внутренний пересчёт. Выход человека из кадра не подтверждает его отсутствие рядом. |
| `R20-B` | Ранее принятые деньги остаются на рабочем месте при следующем обслуживании; пункт 20, абзац второй. | Конкретные деньги прослеживаются от завершённой операции первого клиента до начала обслуживания второго; видны рабочее место и допустимая зона хранения. | Не установлены принадлежность денег, границы операций или способ хранения; продолжается обслуживание того же клиента. |

Предложения из предыдущего исследования `R22` и `R31-4` остаются вне исполняемого каталога. Пункт 22 рассмотрен в контексте приёма, а пункт 31(4) — вместе с исключениями пункта 32 для выдачи по упаковке. Нормативный текст проверен; перед добавлением нужны дата применимой редакции, точный сценарий и подтверждение наблюдаемости на локальных данных.

## Как активировать правило

1. Человек проверяет действующую редакцию официального источника, точный пункт, область применения и исключения. Сохраняет ссылку и дату проверки.
2. На локальных видео подтверждает, что камера показывает все условия для вывода. Положительные примеры должны содержать саму процедуру, отрицательные — похожие допустимые действия. Необходима отдельная проверка другого ракурса и перекрытий.
3. В JSON фиксирует `event_type`, `reference`, `observable_conditions`, `exclusions`, содержательный `verification_note`; устанавливает `verification="verified"`, `verified_on="ГГГГ-ММ-ДД"`, затем `enabled=true`.
4. Передаёт тот же набор ID анализатору и повторяет отложенную проверку. Результаты относятся только к этому набору процедур и версии каталога.

Сервер не принимает включённый кандидат без статуса проверки и даты. Эти поля являются записью ответственного ручного решения, а не автоматическим доказательством правильности правовой интерпретации. Для отдельного локального каталога используйте `APP_RULE_CATALOG_PATH`; исходный каталог можно оставить списком кандидатов.

## Формат правила

```json
{
  "version": "candidate-1",
  "rules": [
    {
      "id": "R20-A",
      "event_type": "Название проверяемого события",
      "enabled": false,
      "verification": "candidate",
      "verified_on": null,
      "reference": {
        "title": "Точное название документа после сверки",
        "clause": "Точный пункт после сверки",
        "source_url": "https://adilet.zan.kz/rus/docs/V1900019680"
      },
      "observable_conditions": ["Все необходимые видимые условия"],
      "exclusions": ["Случаи, при которых вывод делать нельзя"],
      "verification_note": "Что ещё не проверено и почему правило отключено"
    }
  ]
}
```

Идентификаторы уникальны и состоят из заглавных латинских букв, цифр, `_` и `-`. Нормативный источник должен быть HTTPS-ссылкой. Модель возвращает только `rule_id`; название события, документ, пункт и ссылка подставляются сервером. Неизвестное или отключённое правило отклоняется с `failed / invalid_rule`.

Номер телефона, второй человек, передача денег коллеге или наличие пачки на столе сами по себе не образуют перечисленных классов. При нехватке необходимого контекста нельзя выдавать «нарушений нет». Если подтверждённых событий нет, анализатор возвращает `insufficient_evidence`. Независимо подтверждённые события сохраняются со статусом `done / violation`, а частичная область проверки раскрывается в `analysis_scope`. Подробный [контракт интеграции](ml-integration.md) описывает полноту проверки и формат событий.
