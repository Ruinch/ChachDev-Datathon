# Сервисная часть и граница ML

Документ описывает код, за который отвечает человек 1. Человек 2 поставляет локальный анализатор по [согласованному контракту](ml-integration.md). Здесь нет выбора модели, обучения, весов или изменений алгоритма распознавания.

## Полный путь запроса

```text
Браузер: журнал → загрузка MOV → статус → события и доказательства
                         │ X-API-Key, один origin
                         ▼
FastAPI: авторизация → готовность → резервирование обработки
                         ▼
Поток загрузки: лимит размера и общий таймаут → локальный файл
                         ▼
FFprobe: проверка настоящего видео, длительности и параметров
                         ▼
SQLite: задача processing + метаданные
                         ▼
Отдельный процесс: локальный ML-адаптер → проверка контракта
                         ▼
Сервис: каталог правил → исходные JPEG через FFmpeg → done / failed
                         ▼
Браузер: опрос GET → результат, исходное видео, JSON, печать
```

У клиента нет прямого доступа к каталогу данных. Все маршруты `/api/v1/` проверяют заголовок ключа; видео отдаётся защищённым маршрутом с поддержкой Range. Интерфейс получает оригинал авторизованным запросом и использует локальный Blob URL. Ключ хранится только в памяти страницы, не записывается в адрес или экспорт.

## Ответственность модулей

| Область | Код | Что гарантирует сервис |
| --- | --- | --- |
| Сборка приложения | `app/main.py` | Создание и соединение компонентов, жизненный цикл, статический сайт и локальная документация API. |
| HTTP и доступ | `app/http_api.py`, `app/http_guard.py`, `app/api_schemas.py` | Маршруты и схемы, авторизация до чтения загрузки, ограничения потока, ответы ошибок и запрет кеширования API. |
| Сервис задач | `app/job_service.py` | Готовность, резервирование слота, сохранение и проверка видео, передача задачи обработчику, журнал, каталог процедур и доступ к оригиналу. |
| Долговременные данные | `app/storage.py` | SQLite и локальные файлы, метаданные, история, восстановление после перезапуска. |
| Входное видео | `app/video.py` | Проверка медиаконтейнера и длительности реальным FFprobe с таймаутом. |
| Выполнение задач | `app/worker.py` | Один активный анализ, изоляция процесса, ограничение времени, завершение зависшего процесса. |
| Граница анализатора | `app/analyzer.py`, `app/analyzer_readiness.py`, `app/schemas.py` | Проверка структурированного ответа, правил и полноты; проверка доступности runtime встроенного адаптера до приёма файла. |
| Правовая справка | `app/legal_guide.py`, `app/data/legal-guide.json`, `frontend/legal.js` | Объяснение требований и исключений по официальным источникам; версия справки не выдаётся за применённую к старому результату и не активирует распознавание. |
| Доказательства | `app/evidence.py`, `app/rules.py` | JPEG из оригинала; нормативный источник из серверного каталога. |
| Состояние рабочего кабинета | `frontend/session.js` | Единый владелец подключения, ключа, выбранного файла, задачи, маршрута и опроса; отмена устаревших запросов. |
| Представления кабинета | `frontend/app.js`, `frontend/service.js` | Отображение загрузки, журнала, процедур и результатов по состоянию сессии; передача пользовательских действий сессии и печать отчёта. |
| HTTP-клиент и медиа | `frontend/api.js`, `frontend/media.js` | Защищённые запросы с таймаутом чтения ответа, исходный плеер, таймкоды, просмотр кадров и экспорт JSON. |
| Подготовка и запуск | `scripts/` | Среда Windows/Python 3.12–3.13, конфигурация, единое разрешение путей и запуск одного сервера. |

ML-адаптер получает путь локального видео, продолжительность и разрешённые идентификаторы правил. Он возвращает наблюдения с таймкодами и охват проверки. Сервис проверяет результат и извлекает кадры сам. Модель не выбирает произвольный адрес нормативного источника и не создаёт доказательное изображение.

Экспериментальный `app.local_analyzer:build_analyzer` использует отдельный заранее запущенный llama.cpp на loopback. Изолированный процесс каждой задачи создаёт клиент к нему, а не загружает веса заново. Runtime держит веса между заданиями и допускает один запрос одновременно; сервис не добавляет очередь и сохраняет отказ 429 для второго анализа. Время задачи включает инициализацию клиента, декодирование, инференс и JPEG; холодный старт runtime измеряется отдельно и добавляется к полному времени запуска. Адаптеры с загрузкой весов внутри фабрики должны укладывать её в тот же таймаут задачи. Схемы и общий контракт не изменены.

`JobService` отделяет координацию задач от HTTP. Он удерживает слот от проверки готовности до сохранения и передачи существующему обработчику, включая отмену запроса во время записи. Маршруты вызывают его методы и формируют HTTP-ответы; детали файлов и SQLite остаются внутри сервиса и хранилища. Получение оригинала использует отдельное чтение метаданных, без загрузки JSON с кадрами. Подключение анализатора, его схемы, обработчик задач, извлечение кадров, декодер и каталог правил сохраняют существующие контракты.

На стороне браузера только `WorkspaceSession` изменяет подключение, выбранный файл, текущую задачу и маршрут. Сессионный ключ не входит в публичный снимок состояния для представлений. Каждый асинхронный запрос связан с поколением подключения или задачи: после выхода, смены ключа или открытия другой записи устаревший ответ не применяется. Переход в журнал не останавливает опрос принятой задачи; повторный запуск загрузки блокируется до выяснения её состояния.

При временном сбое GET статуса сессия делает до четырёх повторов с задержками 1, 2, 4 и 8 секунд. После исчерпания попыток пользователь может запросить статус вручную; подтверждённые 401 и 404 автоматически не повторяются. POST загрузки не повторяется. Если его ответ потерян или не читается, интерфейс сохраняет выбранный файл и предлагает проверить журнал: задача могла быть принята. Та же подсказка сохраняется, если параллельный 401 отменил незавершённый POST; защищённые данные при этом очищаются.

Охват в карточке результата и печатном отчёте берётся из сохранённого `analysis_scope`: показываются конкретные проверенные ID, при отличии — набор процедур задачи и ограничения. Текущий каталог не подменяет историю старой проверки. JPEG соответствует кадру, отображаемому в исходном видео на запрошенной позиции, включая последний интервал показа; временная отметка остаётся позицией просмотра в оригинале.

## Состояния и отказы

До принятия файла проверяются ключ, готовность инструментов/анализатора/правил и свободный слот. Отказ 401/503/429 не создаёт задачу. Принятая задача имеет `processing`, затем `done` или `failed`; техническая ошибка не получает вердикт `no_violation`.

Для точной фабрики `app.local_analyzer:build_analyzer` готовность дополнительно проверяет импорт PyAV, допустимый literal loopback-адрес и ответ HTTP 200 от `/health` модели. Ожидание HTTP ограничено 0,75 секунды; proxy и редиректы не используются. Проверка не загружает веса и не передаёт видео. `GET /api/v1/system` возвращает `analyzer.runtime={ready, unavailable_reason}`, в том числе при отключённых правилах; у других фабрик `runtime=null` и этой сетевой пробы нет. Перед POST выполняется свежая проверка в отдельном потоке, чтобы ожидание runtime не блокировало HTTP-сервер. При недоступных зависимостях, ошибке адреса или неготовой модели — HTTP 503 без задачи и сохранённого входного файла. Отвечающий runtime подтверждает доступность, но не идентичность весов или качество распознавания; отключённые кандидатные правила по-прежнему запрещают анализ.

Сервис не держит скрытую очередь: второй одновременный анализ получает 429 и может быть повторён после завершения первого. По умолчанию бюджет составляет 30 секунд на загрузку, 15 на FFprobe и 240 на обработку. Их сумма проверяется до запуска и не превышает 295 секунд. Реальное соответствие ТЗ подтверждается измерением на машине с моделью.

После перезапуска незавершённые задачи переводятся в `failed`. Блокировка каталога данных препятствует одновременному запуску второго экземпляра. Для этой архитектуры нужен один процесс Uvicorn с постоянным локальным диском; добавление нескольких API-инстансов требует отдельного решения общей очереди и хранения.

## Эксплуатационные границы

- Один общий ключ открывает все задачи. Пользовательских аккаунтов и разграничения по организациям нет.
- Без локального анализатора и активированных проверенных правил интерфейс работает, а анализ показывает причину неготовности.
- Данные и веса остаются локальными. Автономность анализатора подтверждается отдельным запуском без исходящего интернета.
- Автоматическая очистка данных и резервное копирование не выполняются. Согласованная копия всего каталога делается при остановленном сервере.
- Публичный адрес, HTTPS и автозапуск на выбранном хосте настраиваются отдельно по [инструкции развёртывания](deployment.md).

Сервисные проверки используют синтетические видео и тестовый анализатор. Оценка пропусков, ложных тревог, локализации и применимости нормативов выполняется человеком 2 на локально отложенных данных; сервисные тесты её не заменяют.
