# Подключение локального анализатора — передача человеку 2

Сервис принимает видео, проверяет его метаданные, запускает локальный обработчик, извлекает доказательные JPEG и возвращает результат по контракту ТЗ. Контракт — синхронный метод `analyze(context)` и фабрика без аргументов. Экспериментальная реализация уже находится в `app/local_analyzer.py`, фабрика — `app.local_analyzer:build_analyzer`. Она обращается только к локальному llama.cpp и не читает разметку для предсказаний. Инструкция запуска и фактические ограничения: [ML-передача](ml-handoff.md), [замеры](ml-measurements.md). Ниже сохранён общий контракт для этого и других адаптеров.

## Граница ответственности

| Сервис — человек 1 | Модель и проверка качества — человек 2 |
| --- | --- |
| Загрузка `.mov`, ключ, очередь, сроки обработки, файлы задач | Локальная загрузка весов и инференс без сетевых вызовов |
| Длительность исходного видео, проверка временных отметок | Декодирование последовательностей, поиск и объединение событий |
| Извлечение 1–3 настоящих кадров по временным отметкам | Видимое действие, временная точка, выбранный `rule_id` |
| Нормативное название, пункт и ссылка из каталога | Проверка условий применимости правила и видимости контекста |
| Плеер, отображение ошибок и доказательств | Независимая оценка пропусков, ложных тревог и скорости |

Анализ звука и идентификация лиц не допускаются по ТЗ. Кадры, видео и их описания нельзя отправлять облачным AI-сервисам. Зависимости и веса скачиваются заранее; при обслуживании запросов обработчик работает без интернета.

## Настройка

В отдельном локальном Python-модуле, например `bank_ml/adapter.py`, экспортировать функцию `build_analyzer()`. Модуль должен быть доступен тому Python, которым запущен сервис.

```powershell
$env:APP_ANALYZER_FACTORY = "bank_ml.adapter:build_analyzer"
$env:APP_RULE_CATALOG_PATH = "C:\Datathon\config\verified-rules.json"
```

`APP_RULE_CATALOG_PATH` необязателен: по умолчанию используется `app/data/rules.json`. В нём **нет включённых правил**. Кандидаты требуют проверки источника и локальных видео. Подключение фабрики само по себе не делает сервис готовым к обнаружению нарушений. Состояние анализатора, доступность декодера и активные правила можно посмотреть в защищённом `GET /api/v1/system`.

Фабрика должна вернуть объект с обычным синхронным `analyze(context)`. Некорректный путь, отсутствующий модуль, исключение при инициализации, отсутствие вызываемого метода или `async` вместо синхронного метода приводят к ошибке конфигурации. Инициализация происходит в изолированном процессе обработки; не рассчитывайте на сохранение модели в памяти между заданиями. Замеряйте полный цикл вместе с загрузкой весов.

## Вход анализатора

```python
@dataclass(frozen=True)
class AnalysisContext:
    job_id: str
    video_path: Path
    duration_sec: float
    enabled_rule_ids: tuple[str, ...]
```

`video_path` указывает на локальный исходный `.mov`. `duration_sec` получена сервером из видео, а не из ответа модели. Отметки анализатора должны отсчитываться от начала этого файла в секундах: `0 <= t < duration_sec`. После нарезки окон прибавляйте смещение окна. Не заменяйте исходное видео и не изменяйте его скорость или начало временной шкалы.

`enabled_rule_ids` — весь набор процедур, которые сервис обещает проверять в этой конфигурации. Анализатор не может самостоятельно расширять этот список или придумывать нормативный источник.

## Результат анализатора

Импортировать модели из `app.analyzer`. Можно вернуть экземпляр `LocalAnalysisResult` или словарь, который проходит его проверку. Полный пример структуры для **синтетического теста контракта**, а не готовое обнаружение:

```json
{
  "verdict": "violation",
  "analysis_complete": true,
  "checked_rule_ids": ["TEST-RULE"],
  "limitations": [],
  "violations": [
    {
      "rule_id": "TEST-RULE",
      "timecode_sec": 12.4,
      "description": "Описание действия, которое действительно видно в последовательности кадров.",
      "evidence_timestamps_sec": [11.8, 12.4, 13.1]
    }
  ]
}
```

| Поле | Требование |
| --- | --- |
| `verdict` | Только `violation` или `no_violation`. При первом массив событий непустой; при втором — пустой. |
| `analysis_complete` | Явное `true`, только если проверена вся запись по всем включённым процедурам и нет неразрешённых проблем видимости. По умолчанию `false`. Частичная проверка может содержать подтверждённые положительные события. |
| `checked_rule_ids` | Включённые правила, фактически проверенные анализатором. Каждое событие обязано ссылаться на правило из этого списка. Для `no_violation` требуются все включённые правила и проверка всей записи. |
| `limitations` | Неразрешённые проблемы видимости или полноты. Они запрещают `no_violation`, но не удаляют независимо подтверждённые положительные события. |
| `rule_id` | Идентификатор включённого и проверенного правила из локального каталога. |
| `timecode_sec` | Временная точка наблюдаемого эпизода в исходном файле. |
| `description` | Наблюдаемые действия и контекст; без предположений о личности, намерениях или невидимых деталях. |
| `evidence_timestamps_sec` | От одной до трёх различных конечных неотрицательных временных отметок, строго меньше длительности видео. |

Несколько эпизодов возвращаются отдельными элементами `violations`. Соседние срабатывания одного события объединяет анализатор. Сервер не может определить по JSON, являются ли два похожих наблюдения разными эпизодами.

Модель **не возвращает** `type`, `rule`, ссылки, JPEG, base64 или путь к кадру. Неизвестные поля отклоняются. Сервис берёт `type` и `rule` из каталога и сам извлекает JPEG из исходного файла. Полученные JPEG декодируются для проверки формата и размеров. Это обеспечивает происхождение кадра, но не доказывает, что выбранный кадр по смыслу подтверждает наблюдение: это проверяется на видео человеком и при оценке качества.

## Невидимый контекст и неизвестные события

Если камера не показывает клиентскую зону, границы операции, деньги или иные необходимые признаки, нельзя считать правило проверенным и возвращать `no_violation`. Неизвестное подозрительное действие тоже не превращается автоматически в юридическое нарушение.

В таком случае анализатор должен явно прервать вывод:

```python
from app.analyzer import InsufficientEvidenceError

raise InsufficientEvidenceError(
    "The client area is not visible enough to check the enabled procedure"
)
```

Если подтверждённых событий нет, результат с `analysis_complete=false`, неполным `checked_rule_ids` или непустым `limitations` завершится как `failed / insufficient_evidence`.

Если одно событие независимо подтверждено, а другая процедура или участок записи не наблюдаемы, вернуть `verdict="violation"` с подтверждёнными событиями и честно указать неполноту. Каждое событие должно ссылаться на включённое правило из `checked_rule_ids`; нарушения правил и неверные временные отметки всё равно отклоняются. Сервис сохранит полезные события и передаст ограничения в публичном `analysis_scope`.

Успешный `no_violation` означает **отсутствие обнаруженных нарушений только среди включённых процедур**, после полной проверки записи. Это не утверждение об отсутствии всех возможных банковских нарушений.

## Каркас адаптера для реализации

Следующий фрагмент показывает границу методов; функции загрузки модели и поиска событий необходимо реализовать на локальных данных.

```python
from app.analyzer import AnalysisContext, InsufficientEvidenceError, LocalAnalysisResult

class BankAnalyzer:
    def __init__(self):
        self.model = load_local_model()  # Реализовать; только локальные веса.

    def analyze(self, context: AnalysisContext) -> LocalAnalysisResult:
        if not context.enabled_rule_ids:
            raise InsufficientEvidenceError("No verified visual rules are enabled")
        observations = run_full_video_checks(
            model=self.model,
            video_path=context.video_path,
            duration_sec=context.duration_sec,
            rule_ids=context.enabled_rule_ids,
        )
        # observations фиксирует полноту, видимость и исходные таймкоды.
        return LocalAnalysisResult.model_validate(observations)

def build_analyzer():
    return BankAnalyzer()
```

## Ошибки и публичный ответ

| Код `failed.error.code` | Причина |
| --- | --- |
| `analyzer_unavailable` | Фабрика анализатора не подключена. |
| `analyzer_configuration_error` | Ошибка фабрики, инициализации или каталога. |
| `insufficient_evidence` | Нет активных правил, неполная проверка или недостаточно видимого контекста. |
| `invalid_rule` | Анализатор сослался на неизвестное или отключённое правило. |
| `invalid_analysis_result` | Например, временная отметка вне исходного файла. |
| `evidence_extraction_failed` | FFmpeg не смог получить настоящий декодируемый JPEG. |

Некорректная структура результата, таймаут или авария процесса также дают `failed`; точные коды инфраструктурных ошибок описаны в инструкции развёртывания. У `failed` нет фиктивного `verdict`.

Успешный публичный ответ сохраняет требуемые ТЗ поля: `job_id`, `status=done`, `verdict`, `violations`. В каждом событии остаются `type`, `timecode_sec`, `description`, `evidence_frames` с JPEG base64 и дополнительный `rule` с проверенной нормативной ссылкой. Дополнительный `analysis_scope` явно описывает границы результата:

```json
{
  "full_video_checked": false,
  "checked_rule_ids": ["TEST-RULE"],
  "enabled_rule_ids": ["TEST-RULE", "OTHER-RULE"],
  "limitations": ["Другой участок записи перекрыт и не позволяет проверить вторую процедуру."]
}
```

`full_video_checked=true` выставляется сервером только при явной полноте, проверке всех включённых правил и пустом `limitations`. У `no_violation` это значение обязательно `true`. Интерфейс и экспорт должны сохранять и показывать область проверки, чтобы найденное событие при частичном анализе не выглядело результатом полной проверки всей записи.

Для извлечения доказательств FFmpeg получает только локальные протоколы `file,pipe`; выбирается первый видеопоток без обложек и прикреплённых изображений (`-map 0:V:0`). Это соответствует [официальному описанию селекторов потоков FFmpeg](https://ffmpeg.org/ffmpeg.html#Stream-specifiers).

## Контрольная точка интеграции

1. Локально подтвердить названия событий, применимость источников и видимость необходимых условий; включить только проверенные правила.
2. Запустить адаптер на коротком и самом длинном видео; записать время вместе с инициализацией модели, пиковую память и ошибки.
3. Прогнать через API положительное видео с несколькими эпизодами, отрицательное видео и видео с недостаточной видимостью. Сверить исходные таймкоды и настоящие кадры.
4. Повторить полный цикл без исходящего интернета, без анализа звука и без идентификации лиц.
5. Зафиксировать результаты на отложенных целых видео по [протоколу оценки](model-evaluation.md).
